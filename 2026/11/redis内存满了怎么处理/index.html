Redis 占用越来越高，或已经写不进去时，先确认当前用了多少内存、有没有上限、上限到了会淘汰还是直接报错，再决定改配置还是删数据。不要一上来就 FLUSHALL，也不要在没看过官方说明的情况下套一个“通用百分比”。

本文只讲内存上限、淘汰策略和排查释放，安装步骤见站内Ubuntu安装redis，应用侧用法见phpredis的使用。所有命令输出都来自一次性本地实例，不要在生产数据上复现写满、淘汰或清空。

资料核对日期：2026 年 11 月 25 日。依据当时的 Key eviction、Memory optimization、OOM error、INFO、MEMORY STATS、MEMORY PURGE、CONFIG SET、CONFIG REWRITE。实测版本是 Redis 8.0.2（64 位，jemalloc-5.3.0）。现行文档里另有较新版本才出现的策略和命令，下面会标明本实例不支持的部分。

结论速查

你看到的现象 先看什么 常见处理
写入失败，错误含 OOM command not allowed when used memory > 'maxmemory' INFO memory 里的 used_memory_human、maxmemory_human、maxmemory_policy 只读和删除仍可用。缓存场景可改淘汰策略；需要保留全部键就扩容或删不用的数据，而不是盲目加大上限
内存看起来一直涨 used_memory（Redis 自己的分配）和 used_memory_rss（进程 RSS） 先确认是数据在涨，还是删了键但 RSS 没还给操作系统
改了 CONFIG SET maxmemory，重启后又回去了 配置文件里有没有对应指令 CONFIG SET 只改运行中的值，要持久化需改 redis.conf 或再执行 CONFIG REWRITE
maxmemory 为 0 64 位默认就是不限制 实例可以一直申请内存，官方建议设一个上限，避免把整机吃满

怎么读：

  • used_memory / used_memory_human：Redis 向分配器申请、用于数据的内存。看占用先看这个。
  • used_memory_rss / used_memory_rss_human：操作系统看到的进程常驻内存，和 top/ps 更接近。
  • maxmemory 0：官方 Key eviction 写明，设为 0 表示不对数据集做内存上限。这是 64 位系统的默认行为；32 位系统有 3GB 的隐含上限（本文环境是 64 位，隐含上限未实测）。
  • maxmemory-policy noeviction：到达上限时不淘汰键，写新数据的命令会失败。本实例默认就是它。
  • mem_not_counted_for_evict：复制或持久化缓冲区里、不计入淘汰比较的那部分内存。本实例没有开复制和 AOF，值为 0。
  • mem_fragmentation_ratio：官方说明是 used_memory_rss / used_memory，并提醒其中还包含进程本身的开销。空实例上比值很高，并不等于“碎片已经很严重”。官方还写：当碎片字节数只有几兆时，比值偏高（例如 1.5 以上）也不宜单独当成故障。

MEMORY STATS 给出更细的分项，空实例里 keys.count 为 0，total.allocated 与 used_memory 接近，fragmentation 对应 mem_fragmentation_ratio。日常排查用 INFO memory 通常就够。

本实例在 maxmemory 仍为 0 时写入一个小键是成功的；下面为了安全演示写满，会先加上一个很小的上限，而不会去打满整机内存。

3. 用 redis.conf 或 CONFIG SET 加上限

两种方式含义相同，生效时机不同。

配置文件（启动时生效，重启后还在）：

maxmemory 16mb
maxmemory-policy noeviction

运行中修改（立即生效，默认不会写回文件）：

1
2

redis-cli -h 127.0.0.1 -p 26379 CONFIG SET maxmemory 16mb
redis-cli -h 127.0.0.1 -p 26379 CONFIG SET maxmemory-policy noeviction

本次两次 CONFIG SET 都返回 OK，随后：

1
2
3
4

maxmemory
16777216
maxmemory-policy
noeviction

16mb 会被转成字节 16777216。只做 CONFIG SET 时，这次实验在 SHUTDOWN NOSAVE 后按原配置文件重启，maxmemory 回到 0，maxmemory-policy 回到 noeviction。要把运行中的修改写进配置文件，需要再执行 CONFIG REWRITE，或手工改 redis.conf 后重启。

本次 CONFIG REWRITE 返回 OK，文件末尾被追加了：

# Generated by CONFIG REWRITE
maxmemory 16mb
maxmemory-policy allkeys-lru

同时配置文件里其它运行中的项也可能被重写或补全。再用这份文件启动后，CONFIG GET maxmemory 为 16777216，maxmemory-policy 为 allkeys-lru。重启前应通读改写后的文件，确认没有把不想保留的运行时改动一起写进去。

官方还提醒：如果实例开了复制或持久化，复制/AOF 缓冲不计入与 maxmemory 的比较，建议把 maxmemory 设得略低于机器上能完全交给 Redis 的内存，给这些缓冲区留余地；noeviction 策略下不是同样的必要。本实例没有开复制和 AOF，这一条未在该场景实测。

4. noeviction：写满以后会发生什么

策略为 noeviction、上限 16mb 时，用 8KiB 字符串循环 SET，直到 Redis 返回错误。写入命令可以写成：

1

python3 -c 'print("X"*8192, end="")' | redis-cli -h 127.0.0.1 -p 26379 -x SET noe:0

本次一共成功写入 1536 个这样的键，再写就失败，错误原文是：

1

OOM command not allowed when used memory > 'maxmemory'.

5. allkeys-lru：到达上限后淘汰并继续写入

在已经写满的实例上把策略改成 allkeys-lru：

1

redis-cli -h 127.0.0.1 -p 26379 CONFIG SET maxmemory-policy allkeys-lru

本次改完之后、还没批量写新键时，evicted_keys 已经从 0 变成 4，DBSIZE 从删过 1 个键后的数量落到 1531。说明当实际占用已经达到或略超过 maxmemory 时，换成可淘汰策略后，后续命令处理过程中就可以开始淘汰。

接着又写入 400 个 8KiB 的新键，全部成功，没有再出现 OOM。对比：

项目 改策略后、批量写入前 再写入 400 个键之后
evicted_keys 4 404
DBSIZE 1531 1531
used_memory_human 16.00M 附近 16.00M

键的数量没有随新写入线性增加，evicted_keys 正好增加了 400。这就是“淘汰旧键、腾出空间继续写”。

allkeys-lru 按近似的最近最少使用来选牺牲者，并不是精确的 LRU。本实例默认 maxmemory-samples 为 5，与官方文档里的默认示例一致。另外，Redis 用来记录“最近使用”的时钟粒度是秒级：如果在同一秒内把键全部写入再立刻淘汰，冷热对比会不明显。本次补做了一组更干净的观察：在 noeviction 下写入 1532 个 8KiB 键，等待 2 秒，只 GET 末尾 100 个键，再改成 allkeys-lru 并写入 300 个新键。结果是：

  • evicted_keys 增加 300，DBSIZE 仍为 1532，新键 300 个都还在
  • 刚访问过的 100 个热键全部还在（100/100）
  • 从未再读取的头 100 个键只剩下 58 个（58/100）

热键被保住了，但冷键也不是全部消失，这和官方说的“近似 LRU、抽样淘汰”一致。不要把“最先写入的一定先被删”当成保证。

6. volatile-lru：没有 TTL 的键不会被淘汰

官方写明：volatile-* 系列只在“设置了过期时间（TTL）的键”里淘汰；如果没有任何键带过期时间，行为与 noeviction 相同。

7. 删除键和 FLUSHDB 会释放什么

在确认这是一次性实验实例的前提下，可以删指定键，或清空当前数据库：

1
2

redis-cli -h 127.0.0.1 -p 26379 DEL keep:0
redis-cli -h 127.0.0.1 -p 26379 FLUSHDB

DEL keep:0 返回 1。FLUSHDB 返回 OK，随后 DBSIZE 为 0。used_memory 会明显下降，但进程 RSS 不一定跟着下降。本次清空前 used_memory_human 为 12.81M、used_memory_rss_human 为 25.38M；清空后：

1
2
3
4
5

used_memory:1030200
used_memory_human:1006.05K
used_memory_rss:26607616
used_memory_rss_human:25.38M
used_memory_peak_human:16.05M

used_memory 回到大约 1MB（仍包含启动开销），RSS 仍是 25.38M。这与官方 Memory optimization 的说明一致：键删掉后，内存先还给分配器，分配器不一定立刻把页还给操作系统；规划容量时要按峰值来，而不是按“删完之后 used_memory 看起来很小”。之后如果再写入，分配器通常会先复用已经拿在手里的内存，RSS 不一定继续涨。

这两条命令都会丢掉数据。FLUSHDB 只清当前 DB，FLUSHALL 会清全部 DB。只允许在你自己的一次性实例上做；生产排障应先定位大键和无用键，再有针对地删除。

8. 碎片相关命令：跑了，但不等于已经整理好

官方把真正的分配器外部碎片指标指向 allocator_frag_ratio / allocator_frag_bytes，而不是只看 mem_fragmentation_ratio。删掉大量键之后，比值也往往不准，因为它会受到历史峰值 RSS 的影响。

本次把上限临时调到 32mb，写入 3153 个 8KiB 键（used_memory_human=32.00M，used_memory_rss_human=42.18M），再删掉其中 1577 个偶数键后：

1
2
3

used_memory_human:16.50M
used_memory_rss_human:44.81M
allocator_frag_ratio:1.07

逻辑占用大约砍半，RSS 没有下降（本次还略升到 44.81M）。接着执行：

1

redis-cli -h 127.0.0.1 -p 26379 MEMORY PURGE

返回 OK。官方说明：该命令请 jemalloc 尝试回收脏页；其它分配器上是空操作。本实例分配器是 jemalloc-5.3.0，但执行后 used_memory_rss_human 仍是 44.81M。所以 OK 只表示命令被接受，不保证 RSS 立刻下降。

随后的 MEMORY DOCTOR 指出了三类现象：过去峰值超过当前用量 150%、RSS 相对逻辑分配偏高、分配器外部碎片大于 1.1，并提到可以尝试 MEMORY PURGE，或在必要时重启实例，以及考虑打开 activedefrag。这些是诊断建议，不是已经完成整理的证明。

本次也尝试打开主动整理：

1
2
3

redis-cli -h 127.0.0.1 -p 26379 CONFIG SET activedefrag yes
redis-cli -h 127.0.0.1 -p 26379 CONFIG SET active-defrag-ignore-bytes 1mb
redis-cli -h 127.0.0.1 -p 26379 CONFIG SET active-defrag-threshold-lower 5

默认 activedefrag 为 no，active-defrag-ignore-bytes 默认 104857600（100mb），数据集较小时本来就不会启动。把忽略阈值降到 1mb 并等待约 8 秒后，active_defrag_running 一直是 0，active_defrag_hits 一直是 0。本文把主动碎片整理标为“命令已执行，本环境未观察到整理开始”，不把它写成已经跑通的运维手段。

9. 上限设多少：只有计算思路，没有万能数字

不要用“物理内存的百分之几”当标准答案。可以按下面的顺序自己算，并在目标机器上用 INFO memory 核对：

  1. 先看机器还要给操作系统和其它进程留多少，剩余的才可能给 Redis。
  2. 再看业务峰值需要的数据集大小（按峰值 used_memory 规划，不要按删键之后的低点规划）。
  3. 若开启复制或 AOF，按官方建议把 maxmemory 再留出一块给缓冲区，并观察 mem_not_counted_for_evict。
  4. 接受 RSS 可能高于 used_memory。只盯着 used_memory 等于上限，并不表示进程不会占用更多物理内存。
  5. 64 位上 maxmemory 0 表示不限制。本次在 2mb + noeviction 下写入 110 个 8KiB 键后出现 OOM；再执行 CONFIG SET maxmemory 0，同样的 SET 立即成功，maxmemory_human 变为 0B，used_memory_human 为 2.01M。这次只用于证明 0 会放开上限，没有继续往整机内存里灌数据。官方也写：不设上限时 Redis 可以逐渐吃掉全部空闲内存，因此一般应该配置限制。

缓存可以选 allkeys-lru（或在你验证过命中率后再考虑 allkeys-lfu）；必须全保留的数据应使用 noeviction，并在到达上限前扩容或清理。把上限加大只能延后问题，不能代替找泄漏、大键和不合理的数据结构。

常见问题

写入报 OOM，读还正常，是不是 Redis 坏了？
不是。这是 noeviction（或 volatile-* 但没有可淘汰键）到达 maxmemory 时的预期行为。先看 INFO memory 和 INFO stats 里的 evicted_keys。

改成 volatile-lru 了，为什么还是 OOM？
键上没有 TTL。本次在全部无 TTL 时就是这样。给可丢的键设置过期时间，或改用 allkeys-*。

used_memory 降了，top 里还是很大，要不要立刻重启？
先确认是不是刚删过大批键。官方认为这种 RSS 偏高常常只是峰值留下的，分配器稍后可能复用。本次 FLUSHDB 和“填满再删一半”都出现了 used 下降、RSS 不降。MEMORY PURGE 在本次也没有把 RSS 降下来。是否重启要看机器是否已经因此换页或被 OOM killer 盯上，而不是只看比值。

CONFIG SET 当时生效，第二天重启又回到旧值？
运行中的修改默认不写回文件。改 redis.conf 或在确认内容后执行 CONFIG REWRITE，再核对重启后的 CONFIG GET。

搜到了 allkeys-lrm 或保护某个键不被淘汰的命令？
以你正在运行的版本能 CONFIG SET 成功为准。8.0.2 不接受 *-lrm。现行文档里还有 Redis 8.12 的 BLESS 系列，本实例未涉及，也未实测。

安全注意

  • 实验实例绑定 127.0.0.1、未设置密码，只因为数据可丢。生产必须有认证、网段限制和最小权限。
  • FLUSHDB / FLUSHALL / 无筛选的 KEYS * 加删除，都可能造成业务数据丢失。不要在生产上“先清空试试”。
  • CONFIG REWRITE 会改写配置文件，执行前备份原文件，执行后通读再重启。
  • 不要把真实密码写进命令行、shell 历史或贴到文章里。
  • 把 maxmemory 设得过大，或保持 0，都可能把整机内存吃光，连排查终端都受影响。

回滚

若只是用 CONFIG SET 改了运行中的值，重启且配置文件未改写时，会回到文件里的设置。本次已验证：只 CONFIG SET、不 CONFIG REWRITE，重启后回到默认的 maxmemory 0 与 noeviction。

若已经 CONFIG REWRITE 或手工改了文件，把文件恢复成改之前的副本再重启。需要在运行中先改回去时：

1
2
3

redis-cli -h 127.0.0.1 -p 26379 CONFIG SET maxmemory 0
redis-cli -h 127.0.0.1 -p 26379 CONFIG SET maxmemory-policy noeviction
redis-cli -h 127.0.0.1 -p 26379 CONFIG SET activedefrag no

以上是回到本实例启动默认值的例子，不是生产推荐值。生产应改回你原来的上限和策略，并决定要不要 CONFIG REWRITE。实验进程用 SHUTDOWN NOSAVE 关闭即可，然后删除一次性目录。

实测环境与来源

  • 时间：2026-11-25 09:16–09:24，Asia/Bangkok（UTC+7）
  • 版本：Redis server v=8.0.2，64 位，分配器 jemalloc-5.3.0；本机二进制，未使用 Docker
  • 实例：127.0.0.1:26379，数据目录 /tmp/mmfei-20261125-redis，配置关闭了 RDB/AOF，无认证
  • 已实测：默认 maxmemory=0 / noeviction；INFO memory 与 MEMORY STATS；16mb + noeviction 写满出现 OOM，读和删仍可用；改为 allkeys-lru 后继续写入且 evicted_keys 增加、DBSIZE 不再上涨；等待 2 秒后访问的热键在近似 LRU 下全部保留；volatile-lru 在无 TTL 时 OOM，有 TTL 时只淘汰带过期的键；隔离实例上 DEL / FLUSHDB 使 used_memory 下降但 RSS 未同步下降；MEMORY PURGE 返回 OK 但本次 RSS 未降；CONFIG SET 重启丢失与 CONFIG REWRITE 后重启保留；maxmemory 0 可解除上限（未灌满整机）
  • 未实测：32 位的 3GB 隐含上限；复制/AOF 场景下 mem_not_counted_for_evict 对容量规划的具体影响；allkeys-lfu / volatile-ttl 等其它策略的淘汰效果；主动碎片整理实际回收效果（命令已执行，约 8 秒内未启动）；带密码或 ACL 时 CONFIG REWRITE 的完整文件内容；生产数据上的“合适上限”
